| 23 | `www.sub.<domain>` proxied but HTTPS fails (Universal SSL doesn't cover it) | Cloudflare | Diagnosis: `openssl s_client -connect <host>:443 -servername <host>` gives "handshake failure" (no cert at the edge) while `http://` still 301s into the broken https. Universal SSL covers the root and one level only (`*.example.com`). Fix options: (a) DNS Only if the origin cert's SAN lists the name (check with openssl) plus an origin redirect to the canonical host, free; (b) Advanced Certificate Manager for `*.sub.example.com`, paid; (c) delete the record if unused. Never delete without asking. After switching to DNS Only, test the origin for that exact hostname (`curl -i https://<host>/`): a multi-level www name can return a server-level `403 Forbidden` on every path (nginx default page) while the parent subdomain returns 200 via the same origin, i.e. the host isn't served by the vhost; the fix is a cPanel redirect/alias, not Cloudflare. A cPanel Redirects rule alone may not change the 403, because the `.htaccess` rule is never reached when the vhost does not answer to that name. Next step: create `www.sub.<domain>` as its own domain in cPanel Domains (unshared docroot) and set its redirect to the canonical host; ask first | per site |

## Adding a new entry (end of every attack-review)
1. Confirm the pattern repeats (several requests or several IPs), is not used by the site, and is not already covered by a baseline rule.
2. Pick the layer using the decision table in `attack-review.md`; prefer extending an existing rule.
3. Test: bad path -> 403, legit paths (`/`, `/wp-json/`, `/robots.txt`) -> 200.
4. Add a row here: symptom (what was seen, with path/UA), layer, fix, status `per site`.
5. If the same pattern shows on a second site, promote it: put the rule in `cloudflare-baseline.md` (or the setting in `wordfence-baseline.md`) and mark the row `baseline`. Tell the user about every promotion.
